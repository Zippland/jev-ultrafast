# Jev 实时语音执行可行性调研

日期：2026-09-21。范围：当前 Jev Ultrafast 代码、MiraJelly 流式转写实现、TypeSafe 官方文档，以及真实 Jev API 的纯决策试验。

结论：**可以用 Jev 实现“边说边做”的决策部分，不需要关键词、正则或句式规则判定意图。但现有固定目标循环不能直接接上 partial 转写就投入使用；实时调度、改口处理和真实语音质量还没有完成验证。**

这里的“可行”是结构可行并有小样本模型证据，不代表实时语音 → CU 全链路已经实现。当前语音目录仍为未接入的原型。本次研究没有调用 CU 操作电脑，没有启动麦克风，没有更改独立 CU 或 MiraJelly 仓库。

## 1. 现在程序到底怎样执行

当前主流程是：

```text
一个固定 goal
  + 当前页面 / AX 观察
  + 最近 10 个已执行动作
        ↓
一次 Jev 请求：operation + 各操作的 target 问题
        ↓
仅消费被选中操作对应的 target
        ↓
TYPE_TEXT 时调用文本模型生成字段内容
        ↓
重新检查 UI 是否过期 → 执行一次 → 记录动作 → 读取结果
        ↓
下一轮，直到 DONE / BLOCKED / 预算耗尽
```

代码证据：

- `agent.py:14–42`：创建会话时设置一个固定 goal；`plan` 实际只是包含该目标的单元素列表。
- `model.py:81–148`：Jev 看到页面、元素和最近 10 个动作；没有语音时间线、ASR 修订记录或后续用户消息。
- `model.py:125–132`：同次请求返回多个 target，只使用所选 operation 对应的结果。它们是独立判断，不是前一个问题的答案传给后一个问题。
- `agent.py:133–144`：填字另用文本模型；生成后只重新校验页面，没有校验用户是否已经改口。
- `agent.py:82–83,120–127`：DONE / BLOCKED 终止本轮会话，后续输入不能自然唤醒。
- `questions.py:3–14`：当前说明要求推进完整目标；WAIT 用于界面缺失、禁用或加载，还要求搜索字段准备好就点击。这与持续倾听中的暂缓执行存在冲突。
- `demo.py:66–69`：现有目标入口限制 2,000 字符；不能直接用它承载长语音历史。
- `computer.py:144–177`：CU 适配器保护的是应用、窗口和观察新鲜度，不是用户意图新鲜度。它继续通过独立 MCP 服务工作。

因此问题不只是加一个麦克风按钮。页面没变，不等于上一版语音产生的决定还有效。

## 2. Jev 的能力与边界

Jev 接受文本或结构化 state，可以放入有顺序的用户消息；每次 API 调用评估一个 state，没有持续追加音频的会话接口。时序记忆要由本程序提供。它不直接理解音频。[官方 State](https://docs.typesafe.ai/concepts/state)

现有“操作 + 目标”模式可以保留，并把 LISTEN 作为操作选项。多个问题共享同一输入、并行计算；只有可独立判断的问题适合放在同次调用，不能假设目标问题已经知道操作问题的输出。[官方 fan-out](https://docs.typesafe.ai/patterns/fan-out)

Choice 每题最多 255 个选项，限制的是答案数量，不是语音有多少句。语音是 state，AX 控件是候选。当前 CU 超过单操作 255 个目标会显式报错，不静默丢弃；层级选择尚未实现。[官方 API](https://docs.typesafe.ai/api)

截至本次查阅和调用，实际模型为 `jev-1.13.0`。官方给出的上下文上限是每请求 64k tokens，state 加最长单题 32k；中文接受但准确性不等同于英语。[官方 Models](https://docs.typesafe.ai/models)

官方也明确列出长输入中的无关信息、复杂间接指代、否定等薄弱点。因此“选择器很快”不能推出“它天然懂一整段复杂口语的时序意图”。[官方能力边界](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 3. 纯决策实测

测试先保存题目、预期输出和提示词，再发送请求。预期答案不发给模型；没有根据答案写关键词或正则分支，也没有在轮次之间修改提示词。

- 第一轮：20 个下一步决策、10 个待执行动作判断，共 30 个中文案例。
- 第二轮：追加 10 个无标点、口语、改口和引用案例；另原样重试两个失败案例。
- 原循环对照：6 个相同场景直接调用仓库现有 `choose()`；它没有 LISTEN，也不提供语音时间线，因此用于暴露接入问题，不是等条件排行榜。
- 总计 48 次真实 Jev 请求，55,343 input tokens；没有调用文本生成模型或实际执行任何候选动作。
- 所有用例均为手写的合成文本与合成 UI；不是实际音频，也不是随机抽样评测。

| 组别 | 与预设结果一致 | 说明 |
| --- | --- | --- |
| 第一轮：下一步 | 19 / 20 | 覆盖背景、引用、未说完、先做一步、显式/隐式改口、已执行后转向、ASR 回改、长背景 |
| 第一轮：待执行动作 | 9 / 10 | 覆盖保持、补充背景、换值、撤回、暂缓、旧文本生成结果 |
| 第二轮：新增口语 | 9 / 10 | 沿用第一轮提示词，没有增加特殊句式规则 |
| 两个失败样例重试 | 1 / 2 | 搜索从 LISTEN 变为 CLICK；取消仍被分到 REPLAN |

40 个不同样例共 37 个匹配预设。这只能说明这类语义决策有可行性，不能当作产品准确率，也不足以覆盖所有误操作。

### 已观察到的行为

| 输入或时序 | 实际选择 |
| --- | --- |
| “昨天我让同事打开搜索文档……还没说今天要做什么” | LISTEN |
| “先打开搜索文档，我接着告诉你要找什么” | CLICK 搜索文档 |
| 先要求新建，后来“现成的已经有了，找出来就行” | 转到搜索入口 |
| 待输入“北京方案”，后来说明现在要找“上海方案” | REPLAN，拒绝执行旧值 |
| 待输入“北京方案”，只是补充项目成立背景 | EXECUTE_PENDING，保持原动作 |
| 4,370 字符合成历史背景，随后给出当前指令 | 正确选择当前动作 |
| 当前指令后追加同样长度的历史背景 | 仍保留当前动作 |
| 只有长背景，没有今天的任务 | LISTEN |

### 失败不能省略

1. “现在搜索上海方案”，搜索框已经填好且有搜索按钮：首轮选了 LISTEN，operation confidence 0.11；目标问题正确选中搜索按钮。原样重试选了 CLICK。说明错误可能出在“该不该做”，不在定位。
2. “今天这件事先不做了”：待执行分类选了 REPLAN，而预期是 LISTEN，confidence 0.15；重试仍然如此。它没有选择执行旧动作，但暴露了“取消”和“重规划”两类描述存在重叠。正式接口可以只问“这个待执行动作还能否执行”，弃用后再交给下一轮选择，减少无必要的分类。
3. 追加口语：“有人写了句不要打开搜索文档……那句话是旧文档里的……现在还是按我刚才说的做”：选择 LISTEN，而预期保持打开搜索文档，confidence 0.07。复杂引用与否定仍会让模型迟疑。

这些 confidence 是返回概率分布的统计量，不是结果正确的保证。本次没有事后加阈值把错误变成“通过”。[官方 Confidence](https://docs.typesafe.ai/confidence)

### 原循环的具体问题

- 同一背景叙述选了 CLICK 搜索文档，confidence 0.59。
- “帮我把那个”选 BLOCKED，会终止会话。
- “在文档搜索框里输入”选 TYPE_TEXT，confidence 0.80；这只是选错进入生成步骤，未执行，不能声称实际填了错误文本。
- “填好先放着，等我告诉你搜索时再搜索”选 DONE，会结束当前运行。
- “把搜索框填成上海方案就行，我再想想接下来做什么”，字段已填好，仍选了 CLICK 搜索按钮。

因此直接把不断变化的转写拼进原 goal，确实有把背景当命令、说完一小步就终止或抢先提交的问题。

## 4. 更合适的结构

```text
连续音频 → ASR 分段与修订
                 ↓
程序保存：每个段的最新转写 + 顺序 + 历史版本
                 ↓
最新语音上下文 + 当前 AX + 已执行记录 + 待执行动作/文本
                 ↓
Jev：继续听 / 选择下一操作与目标 / 判断旧候选是否仍有效
                 ↓
若需要填字 → 文本模型生成具体值 → 需要时重新判断候选
                 ↓
独立 CU MCP 执行一步 → 记录事实 → 读取 AX → 下一轮
```

保持两个原则：语义由模型判断；执行事实由程序维护。

**输入不是一串“新命令”。** 同一 ASR 段的新 revision 替换该段旧假设；新的用户语句按时间追加。旧假设保留在日志供诊断，但不当作第二条有效命令。协议的段号、版本号比较只负责还原输入，不决定用户想做什么。

**Jev 决定此刻是否有一个已经明确的下一步。** 不要求用户说完整个任务才允许动手。背景很多时可以 LISTEN；“先打开搜索，我接着说”可以立即选打开搜索。LISTEN 与浏览器加载 WAIT、终止会话分开。

**改口分已执行和未执行。** 未执行的点击或文本候选可以丢弃、重选；已经执行的内容必须保留在事实记录里，模型基于当前 AX 选择如何修改。改写 goal 不能让已经发生的点击消失，也不能假设每个操作都有撤销功能。

**填字仍交给文本模型。** 它需要当前有效语音上下文和所选字段；生成中的用户改口可能使返回文本过时。判断候选时要看具体生成值，而不只是 TYPE_TEXT 这个操作名称。当前原目标形式的 `field_context()` 需要相应调整。

**一次小任务完成后恢复倾听。** 不把当前要求已满足等同于关闭语音会话。执行会话停止与“目前无事可做”是不同状态。

核心语义说明可以很短：

> 根据用户截至目前的真实意图、当前界面和已经完成的动作，选择现在应执行的下一步；如果还没有明确下一步，就继续听。

另一个问题是：

> 结合新增语音，这个具体的待执行动作是否仍然应该执行？

这些说明定义选择题的含义；无需维护“出现不是就取消”“出现帮我就执行”等句式规则。本次实验采用短英文问题说明和中文输入，完整原文已保存。

## 5. 实时调度不能忽略的取舍

MiraJelly 的流式实现可复用的关键是“一个识别任务在运行，只保留一个最新待识别 partial”，而不是对每份草稿排 FIFO 队列。分段协议包含 revision / base_revision，允许稳定文本回退。

源码：

- `/Users/bytedance/Codes/MiraJelly/engine/nerajelly_engine/api/stt.py:122`：稳定/易变文本与回退。
- 同文件 `:311`：单个在途识别任务、最新 partial、final 优先与有界队列。
- `processing/providers/streaming_stt.py:23–31`：partial 采样间隔由 0.48 秒起随段长增长，上限 1.2 秒；这是调度参数，不是实测端到端延迟。

本次 42 次新策略决策（含两次重复）的 HTTP 往返中位数 **548 ms**，P95 **2,282 ms**，范围 **470–3,278 ms**。这些数不包括 ASR、文字生成、CU 操作和最终 AX 验证。

已保存的两个真实计算器 CU 运行分别有 12 / 9 次 Jev 决策，中位数为 549 / 571 ms；它们证明此前 CU 固定目标链路运行过，不能证明实时语音链路。

由此可见：

- 每个转写更新都启动一个独立任务，会积累已经过时的决定。
- 每个转写更新都取消上一次推理，可能使持续讲话时永远无法执行。
- 仅比较 revision 不同就一律作废，无法区分“改了目的地”和“补充无关背景”。

建议单个决策请求在途，合并待处理观察，维护一个可替换的待执行候选；用模型判断新输入是否影响该候选。不把录音结束或固定停顿当作执行前提。

但这也有明确边界：**语义重新判断本身需要时间。** 如果要求每次执行前必须涵盖截至派发瞬间的全部转写，持续输入时就可能反复失效；如果以最近完成的语义判断执行，就存在一个感知到执行的延迟窗口。再加一个审核模型不能消除这个窗口。

因此正式实现需要明确并测量：动作依据哪个输入版本、改口进入转写后多久停止旧目标、是否重复执行、转向后是否修复已改变的状态。不能只记录模型耗时就宣称支持实时打断。

## 6. 长背景怎样处理

4,370 字符的合成背景通过了本次三个位置测试，但不是长时间自然语音验证，也不能推导为上下文越长越好。

先保留原始有序语音记录，不把所有历史无限追加给每次决策。上下文超过可承受范围后，可让 Jev 对有编号的语音片段判断当前相关性，选出要送入行动决策的原文片段；不需要关键词检索或编造命令字符串。相关性选择尚未实现、未在本次评测中验证。

这会增加一次真正有依赖关系的步骤：行动决策若要使用筛选结果，就不能假装在同次独立 fan-out 中已经拿到结果。还必须验证旧约束、跨段改口和代词引用不会被筛掉。原始记录应保留，不能因为暂时无关就永久丢弃。

不建议一开始增加大段规则、固定意图模板、复杂 planner，或把“最后一句”硬当成完整目标。先验证最小语义循环在真实语音下的效果。

## 7. 可执行的下一步与判断边界

推荐沿用现有 AX → choice → MCP，把固定 goal 改为时序输入，并先在可编辑的本地界面回放真实语音。需要验证背景、无标点、改口、ASR 回改、长输入、无关补充、生成文本时改口，以及一项完成后继续提要求。

验收重点不是成功演示一遍，而是同时测到：首个有用动作延迟、错误动作、遗漏动作、改口后仍执行旧动作的次数、重复执行、最后界面是否符合最终意图。保留每个动作关联的语音版本、Jev 原始答案、文本候选和 CU 结果。

**不能许诺的部分：**“打开 A”与“打开 A……不对，打开 B”在前半段完全相同。任何只看到当前信息的模型，都不能既保证在前半段立即执行，又保证永远不会执行后来被否定的 A。合理目标是及时推进已经明确的步骤，并在听到改口后及时停止或修正。

现有证据支持做这个最小原型；不足以认定 Jev 已经能够单独可靠处理所有中文长对话意图。如果真实回放暴露复杂指代和长背景失败，应再评估语义模型或上下文组织方式，不能用越来越多词表补洞。
